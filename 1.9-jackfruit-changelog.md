## [1.9.5-Jackfruit] — 2026-08-28

Licensing. An installation now needs a valid licence key **to receive updates** —
and that is the only thing a licence controls. Nothing in the running CRM is
disabled by an expired, missing, or even revoked licence: no feature is hidden,
no data withheld, no login refused. A customer whose licence lapsed keeps a fully
working app and simply stops receiving new versions until they renew.

### ✨ Added — the licence itself

- **Settings → Licence** (`LicenseSettings.tsx`), a new category in System
  Preferences. Shows the installed key (masked), who it is licensed to, the plan,
  the expiry date with days remaining, seats used out of seats licensed, when the
  licence server last confirmed it, and whether updates are currently allowed.
  Administrators can enter a key, force a re-check, and remove the licence.
- **One field takes two things.** A licence key (`CCRM-XXXX-XXXX-XXXX-XXXX`) and a
  signed *offline token* — for an installation with no outbound internet — go in
  the same box; the backend tells them apart by shape. A key pasted with the
  wrong case, stray spaces, or no hyphens is normalised rather than rejected.
- **An advance-warning banner** (`LicenseBanner.tsx`) above the workspace,
  starting 30 days before expiry (the licence can carry its own window). It is
  deliberately not a modal and not a toast — nothing here justifies interrupting
  someone mid-task, and the whole point of warning early is that there is still
  time. Every wording carries the reassurance that the CRM is unaffected.
  - **Close** hides it for the browser session.
  - **Don't show again** hides it until the *situation* changes — a renewed key,
    or "expires soon" becoming "expired", brings it back. The preference is
    stored per user in `users.metadata_json.preferences`, so it follows the
    account rather than the browser.
  - Everyone sees a lapsing licence; only administrators get the "Enter licence
    key" button, because only they can act on it. An installation that has never
    entered a key at all is shown to administrators only — nobody else needs a
    notice about a purchase they cannot make.
- **Seat limit.** When the licence carries a `maxUsers`, creating a **new** user
  past it is refused — in the settings form and again in `sync.php`, so the
  ceiling is not a client-side suggestion. Accounts that already exist are never
  touched: a licence downgrade stops the team growing, it does not shrink it, and
  an installation with no licence at all has no ceiling.
- **CLI:** `php ccrm license status`, `php ccrm license set <key-or-token>`,
  `php ccrm license check`.
- **`php ccrm update` now checks the licence first** and refuses to pull, with an
  explanation of what to do about it, when the licence is missing, expired,
  revoked, suspended, unverifiable, or has not been confirmed with the licence
  server for over 30 days. It fails **open** when licensing is not configured in
  the build and when CCRM is not installed on that machine yet — refusing an
  update is also a way to leave a customer stuck on a version with a security
  bug.

### 🔐 The trust model

The licence server (a Craft CMS channel plus a small module — see
[`docs/licensing/README.md`](docs/licensing/README.md)) never simply answers
"yes". It returns a **signed token**: the claim, base64url-encoded, plus a
signature over exactly those bytes. CCRM ships the matching public key and
verifies offline. Three consequences worth stating plainly:

- **A substituted licence server is useless.** Hijacked DNS, a TLS-terminating
  proxy, or a replacement server cannot mint a licence — none of them hold the
  private key.
- **Editing the CCRM database is useless.** The stored token is re-verified from
  scratch on *every* read, so setting `licenses.expires_at` to 2099 by hand
  changes a display column and nothing else. Every decision reads the claim
  inside the signature; nothing reads the columns beside it.
- **A vendor outage is invisible to the customer.** Because the cached token
  carries its own proof, the last verified claim stays authoritative while the
  licence server is unreachable — for 30 days as far as *updates* are concerned,
  and for ever as far as the application is concerned, which is never affected.

Three replay defences, because a signed token is a bearer object: the claim names
the installation it was issued for, an online check sends a nonce the server must
echo back inside the claim, and a token is refused if it was issued earlier than
the one already stored.

The signature covers the *encoded* claim rather than the decoded object, which
removes every canonicalisation question — there is exactly one byte string to
verify and it is the one that arrived. The algorithm is taken from the
**configured key**, never from the token, so `alg` cannot be used to choose a
weaker verifier or "none". Ed25519 and RSA-2048 are both supported, and the key
setting accepts several keys at once so one can be rotated across a release.

### 🗄️ Backend

- **`api/license_client.php`** — the shared, output-free library every consumer
  goes through (the HTTP endpoint, `sync.php`'s seat check, and the CLI update
  gate), so the rules cannot drift between them.
- **`api/license.php`** — status for any signed-in user, activation / re-check /
  removal for administrators. Answers in stable status and error **codes**, never
  sentences: all three interface languages live in `translations.ts`, and a raw
  server string can never reach the UI untranslated. Activation is rate-limited
  per IP and globally (`license_attempts`), because a key is a guessable secret.
- **The full licence key is never sent to the browser** — not even to an
  administrator. It is a bearer credential for the vendor's server, the admin
  already has their copy, and an endpoint that hands it back would turn any XSS
  into licence theft. The masked form is enough to confirm which key is
  installed.
- **`licenses`** (one row, `id` pinned to 1) and **`license_attempts`** added to
  `api/schema.php`, so every install path creates them identically.
- **An opaque installation id** is minted once into `system_settings`, letting
  the licence server bind a key to an install without CCRM ever sending anything
  about the customer's data. It is deliberately not derived from the hostname or
  database name — a licence that breaks when a customer migrates their server is
  a support ticket, not a control.
- **Background re-checks are throttled to one every 12 hours** across all
  requests, claimed atomically so N concurrent requests produce one call to the
  licence server rather than N, and a failed check is not retried for 20 minutes.

### 🧪 Testing

- **`src/utils/license.test.ts`** (in `npm run test:unit`) covers the pure
  decision layer: parsing an untrusted payload, when the banner appears, how a
  dismissal is keyed to the situation rather than to the banner, and the seat
  arithmetic. It includes the case where the QA harness's generic
  `{ success: true, data: [] }` must **not** be read as a licence state.
- **`scripts/test/license-verification.php`** — 94 checks over the licensing
  backend, run against real keypairs in both algorithms and a throwaway MySQL
  database: signature verification, tamper and replay rejection, algorithm
  confusion, key rotation, malformed tokens, how a licence-server answer is read,
  the whole state machine, and the seat ceiling. Deliberately outside `npm test`,
  whose contract is "no Docker, no PHP, no database required".
- The Craft-side signer and the CCRM-side verifier were exercised **against each
  other** with the shipped scripts, which is what caught a `getopt` bug in
  `mint-offline-token.php`: `--expires 2027-08-28` was silently discarded and the
  script cheerfully issued a token expiring 1970-01-01.

### 📄 Docs

- **[`docs/licensing/README.md`](docs/licensing/README.md)** — the trust model,
  the claim format, the Craft channel's fields, keypair generation, and the
  operating notes (revoking a licence, a customer who rebuilt their server, one
  key across staging and production).
- **`docs/licensing/craft-module/`** — a drop-in Craft module (route, controller,
  signer), a keypair generator, and an offline-token minter. Written for the
  licence server but **never run against a live Craft install** — review it
  before trusting it with real keys.
- **`.agents/rules/licensing.md`** — what a licence is allowed to control, and
  what it must never touch.

### ⚠️ Before shipping this to customers

`CCRM_LICENSE_PUBLIC_KEY` is **empty** in this build. Until a real key is
compiled into both `api/license_client.php` and `public/api/license_client.php`,
the product reports "licensing is not configured": no banner, no seat limit, and
`php ccrm update` warns but proceeds. That is the correct behaviour for an
unreleased build and the reason the step is not optional for a released one — see
the setup guide.

## [1.9.4-Jackfruit] — 2026-08-28

Two dark-mode contrast bugs left over from the 1.9.3 theme switcher.

### 🐛 Fixed

- **Sidebar and Start Menu icons with inconsistent contrast in dark mode.**
  Module icons (`Sidebar.tsx`, `StartMenu.tsx`) were colored with raw hex
  literals in an inline `style`, so they never rode the app's automatic dark
  palette inversion the way every `text-*`/`bg-*` class does. Colors that are
  dark-on-purpose in light mode — `Sklad` (blue-900 navy) and `Nastavenia`
  (slate-600) — stayed dark on the near-black dark background and read as
  nearly invisible next to every other icon. Swapped the hex literals for
  `var(--color-<ramp>-<shade>)` references to the same Tailwind shades, so
  these icons now lighten in dark mode exactly like `text-blue-900` would.
- **White halo around colored button/badge shadows in dark mode.** A solid
  button's glow (`shadow-lg shadow-blue-950/20`, `shadow-indigo-600/30`, …)
  reads `--tw-shadow-color` from the same `--color-<ramp>-<shade>` variable a
  `bg-*` utility uses. The dark palette inverts that variable for legibility
  as *text* (900/950 becomes near-white), but `scripts/postcss-dark-palette.mjs`
  only pinned that inversion back for `background-color`/border/glyph
  properties — not for shadow color — so any solid button's colored glow
  turned into a stray white halo. Added `--tw-shadow-color` to the plugin's
  `SURFACE_PROPS` so shadow colors pin back to their original saturated value
  the same way background fills do.

## [1.9.3-Jackfruit] — 2026-08-28

Dark mode. A theme switcher in Personal Settings with four appearances — System,
Light, Dark and Auto — where Auto follows the real sunrise and sunset for the
user's location. The dark palette is applied to the whole application, not to a
handful of screens, and the legibility of every module in it is now asserted by
the QA suite on every run.

### ✨ Added — the appearance switcher

- **Four appearances**, in `Osobné nastavenia → Základný profil → Vzhľad`:
  - **System** — follows the operating system / browser `prefers-color-scheme`,
    and re-paints live when the OS setting is flipped, without a reload.
  - **Light** and **Dark** — an explicit choice that ignores everything else.
  - **Auto** — light between sunrise and sunset, dark through the night. The
    panel shows today's two times and where they came from.
- **The appearance and the light palette are independent.** Switching to dark
  and back returns the herb theme (Basic / Sezame) the user had chosen; the
  palette picker now says so, and describes what it applies to.
- **The choice follows the account.** It is written to
  `users.metadata_json.preferences.themeMode` and adopted on login from any
  browser, while a localStorage mirror lets `index.html` paint the right theme
  before the bundle has parsed — so a dark boot never flashes a white screen.
- **`color-scheme` is set on the document**, so scrollbars, date pickers,
  `<select>` popups and form autofill follow the theme instead of punching white
  holes into a dark screen. The `theme-color` meta tag is kept in step for the
  mobile address bar.

### 🌅 Added — sunrise and sunset without a weather API

- **`src/utils/solar.ts`** implements the standard NOAA/USNO sunrise equation:
  sunrise, sunset, solar noon and the polar day/night cases are a closed-form
  function of date, latitude and longitude. No API key, no network round-trip on
  boot, no rate limit, and nothing that can fail while the user is offline.
  Verified against published times for Bratislava at both solstices, plus
  hemisphere, equinox and arctic-circle properties (`solar.test.ts`).
- **Location**: the browser's own geolocation when the user grants it (a "use my
  location" button in the panel), otherwise a longitude derived from the time
  zone — accurate to a few minutes at mid-latitudes, which is all a theme switch
  needs. Nothing is sent anywhere; the coordinates stay in the browser.
- **It sleeps until the next transition** instead of polling, re-checks when a
  suspended laptop wakes or the tab is looked at again, and re-arms itself after
  every flip.

### 🎨 Added — the dark palette

- The app's markup uses ~13 000 raw Tailwind palette classes (`bg-white`,
  `border-slate-200`, `bg-indigo-50 text-indigo-700`) rather than semantic
  tokens, so dark mode is built by **re-pointing the palette** instead of
  annotating markup: Tailwind v4 compiles every colour utility to
  `var(--color-<ramp>-<shade>)`, and `src/index.css` turns each ramp inside out
  under `[data-theme="dark"]` — the light end that carries surfaces becomes
  dark, the dark end that carries type becomes light.
- **`scripts/postcss-dark-palette.mjs`** covers the cases where one variable has
  to be two things at once — a saturated shade used as a solid button fill has
  to stay deep, the same shade used as text has to lift. It reads the utilities
  Tailwind has just generated and derives the overrides from them, so every
  variant (`hover:`, `focus:`, `group-hover:`, `peer-checked:after:`, …) is
  handled and **markup written after today is covered with nothing to maintain
  by hand**.
- **`src/utils/accentColor.ts`** handles the colours that come from the
  database as inline styles and therefore have no variable to redefine:
  `liftAccent()` lifts a configured pipeline-state / lead-source / project-
  manager colour towards white in dark mode (and is a no-op in light),
  `readableOn()` picks the legible foreground for a configured badge fill.

### 🚑 Fixed — legibility, in both appearances

- **The "add lead" modal and the client drawer painted themselves white** with a
  hardcoded inline `background: #ffffff`, which no palette can reach. Both now
  use the card token, so the panel follows the theme.
- **White labels on pale configured colours** — a `#0ea5e9` project type or lead
  state carried white text at 2.8:1 **in light mode too**. The foreground is now
  measured from the fill (`readableOn`), fixing both appearances at once.
- **The inactive pipeline-state chips** were hardcoded `#f8fafc` / `#e2e8f0` /
  `#94a3b8` and stayed white-on-white in dark. They use the theme tokens now.
- **Canvas charts** (client financial report, dashboard widgets) had their axis,
  grid and legend colours baked in as light-mode literals — invisible ticks and
  bright white grid lines on a dark card. They are rebuilt from the appearance
  and re-render when it flips.
- **Text with no colour of its own inherited `text-slate-100` from `<body>`**,
  a leftover from a dark starter template that made such text nearly invisible
  on the light screens too. The body now inherits the theme's foreground.

### 🧪 Added — the audit knows about dark mode

- **`tests/e2e/darkmode.spec.ts`** (`npm run test:qa:dark`) opens every module —
  and the client drawer, the new-lead modal and the create-task drawer — with
  the appearance forced to dark, then measures every run of text against the
  surface actually painted behind it, flattening translucent layers on the way.
  Below 3:1 a label is not dim, it is gone.
- **It measures the same screen twice.** After the dark pass the theme attribute
  is flipped to light on the very same DOM — no reload, so every element keeps
  its identity — and measured again. What fails the run is what dark mode
  *broke*: legible in light, not legible in dark. Text that is equally hard to
  read in the light theme the app already ships (white on a `bg-amber-500` pill
  is 2.1:1 either way) is printed as a note instead of failing a suite that
  cannot fix it. Every fix listed above was found this way, including two bugs
  in the PostCSS pass itself — a hover colour that painted at rest, and alpha
  utilities such as `bg-white/50` that were never re-themed at all.
- Verified against a full audit of the previous commit run side by side: the
  same 79 pre-existing findings, before and after.

## [1.9.2-Jackfruit] — 2026-08-27

Made the automated QA audit a first-class, discoverable part of the workflow. The
suite itself was written in 1.8 (v1.8.31–v1.8.33) but had never been merged into
1.9, was documented only in an agent-only skill file, ran nowhere automatically,
and saved its results in a way that quietly orphaned its own evidence.

### ✨ Added — the suite is now present and reachable on 1.9

- **Ported the QA audit onto 1.9.** `tests/`, `playwright.config.ts`,
  `tsconfig.qa.json`, `scripts/qa/` and the `ccrm-qa-audit` skill existed only on
  `1.8-imbe-fix`; `1.9-jackfruit` forked at v1.8.30, one commit before the QA work
  landed, so `npm run test:qa` did not exist on this branch at all. Ported without
  the 1.8 version/changelog commits.
- **`docs/TESTING.md`** — one human-facing guide: setup, every command, the
  environment switches, where results go, how to read them, how to add a test
  (including Chrome Recorder journeys, which need no code), and how to triage a
  finding.
- **README has a Testing section** and a "new here?" pointer, so the entry point a
  developer actually opens now leads somewhere. Removed the leftover Vite starter
  template boilerplate that had been sitting at the bottom of the file.
- **`CLAUDE.md`** — orients AI agents to the tests and the workflow rules.
- **`.agents/rules/qa-before-ship.md`** — the rule, with what to run during
  development versus when a change is finished.

### ✨ Added — it now runs on its own

- **`.github/workflows/qa.yml`** — the repository's first CI. Runs `tsc -b`, the
  QA type-check, `npm run test:unit` and `npm run test:qa` on every push and pull
  request. No secrets and no database: the suite mocks `/sync.php`, `/api/*` and
  `/upload.php`, so a clean runner needs only Node and Chromium. It runs the same
  npm scripts a developer runs, so a red build reproduces locally with one command.
  Uploads each run folder and the Playwright traces as artifacts, and prints the
  verdict to the workflow summary page.
- **`npm run deploy` gates on the tests** and aborts before building, committing
  or pushing if they fail. `DEPLOY_SKIP_QA=1` is the hotfix escape hatch.

### 🚑 Fixed — the QA suite could silently audit another branch

- **The audit ran on the shared Vite port with `reuseExistingServer: true`.** With
  several git worktrees checked out, a dev server from a *different branch* on
  5173 would be reused and audited instead of the branch under test — and when
  that server went away, every test failed with `ERR_CONNECTION_REFUSED`. Observed
  in practice: a second checkout's Vite had auto-incremented onto 5174.
  The audit now runs on its own port (**5273**, deliberately outside Vite's
  5173→5174→5175 auto-increment path) with `--strictPort` and no implicit reuse,
  so a run either audits this checkout or refuses to start. `QA_PORT` and
  `QA_REUSE_SERVER=1` override.
- **`BASE_URL` still started a pointless local dev server** when auditing a
  deployed environment, and waited on a port nothing would use. The web server is
  now skipped entirely when `BASE_URL` is set.

### 🚑 Fixed — results no longer overwrite or orphan each other

- **Screenshots were never cleaned and never archived.** Reports were archived to
  `qa-history/`, but every run's screenshots piled into one shared flat
  `test-results/screenshots/` forever, so an archived report linked to evidence
  mixed in with every other run's — and the PNGs grew without bound.
  Every run now writes a self-contained folder,
  `test-results/runs/<timestamp>-<kind>/`, holding `report.md`, `findings.json`
  and that run's `screenshots/`, with links relative to the folder. A run folder
  can be zipped, attached to a ticket or downloaded from CI and still renders.
  Old folders are pruned to `QA_KEEP_RUNS` (default 10).
- **The latest run is still always** `test-results/qa-audit-report.md`, and a
  filtered run still never overwrites `qa-audit-report-latest-full.md`.

### 💅 Improved — the result is visible when the run ends

- The terminal summary now opens with an explicit **`RESULT: PASSED` /
  `RESULT: FAILED`** verdict, the severity counts, the top findings, the run
  folder and the exact command to reopen the report as a clickable `file://` link.
- **Canary findings no longer read as failures.** Canaries pass *when* they detect
  their known product bug, so their findings are now excluded from the verdict and
  labelled as expected detections — previously the summary said `FAILED` on a run
  Playwright reported as passed.
- **Silenced the Vite dev-server firehose** (deprecation warnings forwarded from
  the browser) that buried the run's own output. `QA_SERVER_LOGS=1` restores it.
- `npm run test:qa:report -- --list` lists the saved runs and what each found.
- `QA_OPEN=1` opens the report automatically when defects are found.

### 🔧 Changed

- **`npm run test:unit` now exists.** `src/utils/taskSelectors.test.ts` had been in
  the tree with no way to run it from npm — 8 passing assertions nobody could
  execute. `npm test` runs the unit tests and the QA audit together.
- `@playwright/test` added to devDependencies; `test-results/` and
  `playwright-report/` git-ignored.
- `GEMINI.md` and the `ccrm-qa-audit` skill updated for the new ports, run folders
  and commands; the Chrome Recorder guide now names `npm run test:qa:recorder`.

### 📋 Known state

A full audit of 1.9 passes 128 checks and reports 79 findings (52 HIGH, 9 MEDIUM,
18 LOW). 44 of the HIGH findings are `DROPDOWN_OCCLUDED` — consistent with the
single known stacking-context bug the `Čas termínu` canary pins. These are
pre-existing product defects surfaced by the audit, not regressions from this
change, and are left for a dedicated fix pass.

## [1.9.1-Jackfruit] — 2026-08-27

Audit and hardening pass over the 1.9 Invoices & Price Offers section. It shipped
looking unlike the rest of the app, with a backend that never reached the deployed
artifact, and several release blockers.

### 🚑 Fixed — release blockers

- **`sync.php` was a PHP parse error.** The 1.9 invoicing read-block was inserted one
  closing brace short, so the whole sync endpoint — every read and write, for every
  section — returned a fatal. The CRM could not load or save any data at all.
- **The backend never shipped.** `public/` is the deploy source of truth (`php ccrm
  update` copies `public/` → `dist/` → docroot), but the 1.9 work only touched the root
  mirrors. The built artifact contained no `invoices_offers` sync, no invoicing tables
  in `schema.php`, and none of `superfaktura.php` / `idoklad.php` /
  `generate_pdf_template.php`. Every price offer would have been silently discarded.
- **Settings crashed.** The Invoicing tab referenced `FileText`, `Building2`,
  `Sparkles` and `cn` without importing them; the Unified Entries tab lost its
  `settingsAction` / `settingsActionId` props. Both threw on render.
- **Settings → Projects lost its content.** The `<ProjectSettings />` block was deleted
  while the tab stayed in the navigation, leaving it blank. Restored.
- **`VERSION_CODENAME` was dropped** from `version.ts` while `RagAiView` still imports
  it at module scope, naming the RAG assistant `undefined`. Restored — and
  `increment-version.js` no longer overwrites the file (it also used to reset any
  codenamed version to 1.1.0).
- **`api/chat_rag.php` was a PHP parse error** in the root mirror, from an unterminated
  `try` block introduced in v1.8.14. The RAG chat endpoint returned a fatal.
- **Root and `public/` backends had diverged in both directions** — root ahead on
  invoicing, `public/` ahead on the v1.8.26–v1.8.30 RAG work. Reconciled to the union
  (the autonomous-agent warehouse RAG block was merged into the newer copy), so a
  publish no longer leaves the checkout dirty and blocks the next `ccrm update`.
- **`pushStateToServer` argument shift.** The post-re-login replay passed its options
  object into the `nextInvoicesOffers` slot, corrupting the replayed payload.

### 🐛 Fixed — correctness

- iDoklad price offers always failed: the connector accepted only
  `create_price_offer` while the UI sends `create_estimate`. Both names now work.
- iDoklad ignored its Sandbox toggle and issued **real** documents against the
  production API. It now uses the sandbox identity and API hosts.
- iDoklad created a duplicate contact for every document; it now looks the partner up
  by IČO (or name) first, and fails loudly instead of posting with `PartnerId: 0`.
- iDoklad sent DIČ in the VAT-number field; it now sends IČ DPH. The country id is
  derived from the client's country instead of being hardcoded.
- The AI custom template was never applied — `CustomAiOfferTemplate` was rendered
  without its `customTemplate` prop, so every "AI" document came out with defaults.
- Invoices were titled "Predbežná cenová ponuka": the title was fixed at mount and
  never re-derived when the document type changed.
- Document numbers came from `list.length + 1`, handing out duplicates as soon as a
  document was deleted. They are now derived from the highest number in the series.
- Editing an already-issued external document re-posted it to the accounting service.
- Deleting your only price offer silently failed: the mass-delete circuit breaker
  treated an explicit, user-initiated delete as an empty/stale push. Explicit delta
  deletions may now empty an ordinary table; delete-by-omission is still blocked, and
  `strict` tables (users, project types) are still never emptied.
- Dates were derived from `toISOString()` (UTC), filing anything issued after local
  midnight under the previous day. They now use the local-time helpers.
- Money and dates ignored `systemCurrency` and the user's language — `EUR` and `sk-SK`
  were hardcoded throughout, including on the printed document.

### 🔒 Fixed — security

- **Accounting credentials were exposed.** `INVOICING_INTEGRATIONS` (SuperFaktúra API
  key, iDoklad client secret) was stored in plaintext and sent unmasked to every
  authenticated client on every sync, whatever their role. Secrets are now encrypted at
  rest and masked outbound, matching `INTEGRATIONS_CONFIG`; saving a masked value keeps
  the stored secret, and the connectors decrypt server-side.
- Company billing settings and invoicing integrations were wiped whenever a client
  saved settings without including them. Omitted keys are now left untouched.
- **Another company's identity was baked in as the default.** An unconfigured tenant
  issued price offers carrying a real third party's name, address, IČO/DIČ/IČ DPH,
  phone numbers, email and client references. All removed — the templates omit whatever
  Settings leaves blank, and the section shows a setup notice instead.
- AI-generated template colours are validated as hex before reaching a style attribute,
  section ids are allow-listed, and text fields are length-capped.
- External API calls now have connect and total timeouts with abort handling, instead
  of hanging the wizard indefinitely.

### 🎨 Changed — UI/UX unified with the rest of the app

- The section rendered inside its own `p-4 sm:p-8 max-w-7xl mx-auto` wrapper on top of
  the layout's own padding, making it narrower than every other section and
  double-padded. It now uses the standard `space-y-6 pb-16` root.
- **It was the only screen in the app with a dark theme.** It carried 157 `dark:`
  utilities, and Tailwind v4 resolves those against `prefers-color-scheme` (the
  `darkMode: "class"` config is never loaded — there is no `@config`), so on an OS in
  dark mode this one section went dark while everything else stayed light. All removed,
  and the `dark:` variant is re-pointed at the app's own `data-theme` mechanism so a
  stray utility cannot do this again.
- The section header now matches the app's standard title row instead of a bespoke card.
- Native `<select>` elements replaced with the app's `CustomSelect`.
- `alert()` replaced with the app's toast; confirmations are localised.
- Full EN/SK/HU translation — the section was hardcoded Slovak and ignored its
  `systemLanguage` prop entirely.

### ✨ Added

- Editing an existing document, and changing its status from the list — status was
  filterable but could never actually change, so the win-rate KPI was permanently 0 %.
  Win rate is now measured over decided offers only.
- Print/PDF outputs just the document. `window.print()` used to spool the whole app

- New documents are pre-filled from Settings → Invoicing (VAT rate, payment terms,
  warranty, duration, start date, next steps, USP cards) instead of carrying hardcoded

- Settings → Invoicing gained the default VAT rate, project duration, start date,
  next-steps text and USP card editor that the 1.9.0 notes promised but never rendered.
- The warehouse picker is searchable instead of listing only the first 8 products.
- Line-item discount is editable, and the document shows the net/VAT split.
- iDoklad documents fetch and store the server-rendered PDF, linked from the preview.
