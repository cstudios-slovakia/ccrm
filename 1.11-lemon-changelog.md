# Update 1.11 (Codename: Lemon) — New Features

### v1.11.155-Lemon (2026-10-08)
- **MCP Gateway: Permission Enforcement, Finance Maths and 27 New Tools (`api/mcp.php`, `api/mcp_ext.php`, `api/mcp_ext_ops.php`, `api/mcp_ext_writes.php`, `api/mcp_keys.php`, `PersonalSettingsView.tsx`, mirrored in `public/api/`)**. This release closes the findings of the MCP data-access audit.
  - **A Key Can Only Do What Its Owner's Role Can**: Until now any valid MCP key could call every tool, whatever the owner's role. Every tool now maps to the module permissions it needs (view, edit, and the side-effect modules it writes to); a tool missing from the table is denied. `tools/list` only offers the tools a key may call, and a call outside the role answers `-32003 Forbidden`. Sub-permissions are honoured: without `employees.salaries` the PIN, salary fields, contract files and notes are stripped and the payroll tools disappear; without `tasks.view_all` a key only sees tasks the owner owns, created or is assigned to; `get_client`, `get_project` and `search_entities` only embed modules the role can see. **Existing keys of Viewer-type roles lose their write tools; tell the people who use them.**
  - **Key Hardening**: A key created before its owner's last password reset is rejected. Key creation and revocation are written to the audit log (they never were: the helper they called did not exist), audit rows from MCP are marked `[via MCP key <id>]`, and an admin can list and revoke other users' keys through `GET /api/mcp_keys.php?all=1` and `DELETE ...?user_id=`. The key prefix now fits its `VARCHAR(20)` column, so keys can be generated on a strict-mode database again. The wildcard CORS header is gone and database errors reach the client as `Database error (ref <id>)` instead of SQL text.
  - **Stale Claims Corrected**: "Zero access to system settings" was false (`set_financial_mode` writes a setting); it is now admin-only and the copyable agent prompt, the security note (EN/SK/HU) and the tool-count comments say what is true. The hard-coded developer path in the example MCP configuration is a placeholder.
  - **Write Paths Follow the App's Own Rules**:
    - *Invoices*: `create_invoice` no longer fails half-way (it wrote a column that does not exist and left an orphan header). Lines are net with VAT added per line, numbers follow `FA-YYYY-NNN`, duplicates are refused, the invoice and its linked ledger movement `fr-inv-<id>` are written in one transaction, and nothing is booked as received. `update_invoice_status` only sets draft, sent or cancelled; approving, invoicing and settling money stay in the app.
    - *Expenses*: recorded as planned or pending only.
    - *Stock*: `adjust_stock` creates `PRI`/`VYD`/`INV` documents, updates the weighted average cost on receipts, records cost, sell and profit on sales, and refuses to go below zero or to issue reserved stock.
    - *Payroll*: `record_salary_payout` mirrors the app: items breakdown, linked payroll expense for auto-expense employees, and a paid period can no longer be overwritten.
    - *Leads and clients*: stage moves are checked against the configured stages and the open-blocking-task guard, and write the same history entry as the lead list. `list_clients` returns client profiles as the Clients register shows them (grouped by name, with the value adjustment) instead of every lead; `create_client` and `convert_lead_to_client` create `client-*` records.
    - *Projects, tasks, vacations*: statuses must be configured ones, a completed status stamps the finish date, `value`, `delay_reason`, `rating` and `division` can be read and written; new tasks start in the first configured status and are completed into the configured done state; leave cannot overlap, must use a configured type, and is logged as requested by default. `list_projects` no longer fails when filtered by status or search.
  - **28 New Tools (81 in total)**: `get_project_billing_summary`, `get_invoicable_summary` (also reports the dashboard tile's own figure as `dashboard_basis_total`), `get_financial_overview`, `list_financial_movements`, `list_financial_categories`, `list_recurring_movements`, `get_cash_flow_forecast`, `get_invoicing_metrics`, `get_client_profile`, `list_client_categories`, `get_lead_pipeline_summary` (with SLA breaches), `set_task_assignees`, `set_task_tags`, `get_meeting`, `list_meeting_tasks`, `get_warehouse_metrics`, `list_warehouses`, `list_suppliers`, `list_stock_movements`, `list_batches`, `get_vacation_balance`, `get_payroll_summary`, `list_workflows`, `get_workflow_runs`, `list_unified_entries`, `get_unified_entry_rows`, `list_files`, `list_documents`. `get_financial_summary` now uses the Finance overview model (cash basis, cancelled rows excluded, recurring rules expanded). `list_tasks` gained time buckets and a created-date range. Assignee and tag tools only add; no MCP tool deletes anything.
  - **Tested Against the App's Own Formulas**: The finance, billing, forecast and equation maths are PHP ports of `financialOverviewTable.ts`, `recurringExpenses.ts`, `futureMovements.ts`, `projectBilling.ts` and `equationEvaluator.ts`. The new `npm run test:mcp` probe runs the TypeScript originals and the PHP on one fixture and fails on any difference; it also checks roles, field stripping, write paths and that no MCP file deletes rows, on a scratch database cloned from the dev one (TESTING.md 5d). It found and fixed a defect in this very release: the employee field filter used a constant that was never defined when the request ran.
