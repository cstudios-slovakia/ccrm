# Update 1.14 (Codename: Orange) — New Features

This document tracks all new features, architectural changes, schema migrations, and improvements introduced in the 1.14 Orange update cycle.

Builds made on the `1.14-orange` branch before the switch (the Tremor Blocks remake, the css-main merge: Time Tracking v2, the performance dashboard, GitHub) are still listed under 1.13 in `1.13-nectarine-changelog.md`, up to `v1.13.105-Nectarine`.

### v1.14.0-Orange (2026-11-23)
- **Release Cycle 1.14 (Orange) Initialization (`src/utils/version.ts`, `1.14-orange-changelog.md`, `GEMINI.md`, `changelog.d/README.md`, `.agents/rules/commit-and-versioning.md`)**:

### v1.14.1-Orange (2026-11-23)
- **Header: the timer pill is as tall as the buttons beside it** (`src/components/timeTracking/HeaderTimerPill.tsx`, `RoundTimerButton.tsx`): the running pill, the Start and the Resume button were 4–8 px taller than the header controls (`h-10`/`h-11` against `h-8.5`, `h-9` and `h-10`). They now use the header's own heights at every width, and so match at every View size, with the header's `rounded-md` corners; the round Stop button in the pill has its own smaller size so it fits with a 2 px gap, and the presence ring, the `+N` count, the project line and Resume keep working. The phone timer sheet is unchanged.
- **Time Tracking: the project picker shows project names again** (`src/components/timeTracking/ProjectPicker.tsx`): the css-main merge left the search row's `</div>` below the footer, so the project list and the "Show finished" footer rendered inside the narrow search row: only the colour dots were visible, the list spilled out of the popover and the search box sat at the bottom. The closing tag is back after the search row, as in both merged branches.
- **One path records a reopened task** (`public/api/task_done.php`, `public/api/project_breakdown_migrations.php`, `public/api/mcp_ext_writes.php`, `public/sync.php`): `ccrm_task_record_reopen()` is now the only writer of both `tasks.reopens_json` and `tasks.reopened_count`, so the project breakdown (rework per project and employee) and the performance dashboard (Rework ratio and count) can no longer disagree. Saving in the app, the MCP `update_task` tool and the project-breakdown hook all call it, inside the same transaction and row lock; the server reports `reopenedCount` as the larger of the counter and the log length. Ticket reopen counting is unchanged.
  - The Rework metrics only know reopenings recorded since the log was introduced: older reopenings keep their count but have no timestamp, so they still show in the project breakdown and not in the dashboard's period figures.
  - A stale completion stamp on a task that is already open no longer counts as a reopening (the rule the log already used).
- **Tests**: `scripts/test-task-reopen.php` (`npm run test:task-reopen`): sync, MCP and legacy rows all end with the counter equal to the log, a first completion does not count, no other code increments the counter.
- **Performance dashboard cards restyled to the Tremor look** (`src/components/dashboard/performance/*`): `slate-*` to `gray-*`, crisp radii (`rounded-md` buttons and inputs, `rounded-lg` cards), entity-accent tokens instead of `bg-primary`; class strings only.
- **GitHub project fields, acceptance criteria and GitHub settings restyled to the Tremor look** (`ProjectAcceptanceCriteria`, `ProjectPushTimelineItem`, `ProjectGithubFields`, `GithubIntegrationSettings`, `TaskStateTimerActionSelect`): gray palette, crisp radii (`rounded-md` buttons and inputs, `rounded-lg` cards; the acceptance-criteria input loses its double border), entity-accent tokens instead of `indigo-*`; class strings only.
- **Time Tracking: the css-main screens use the Tremor look** (`src/components/timeTracking/*`: Calendar popover and task rail, Reports filters and summary table, project time overview, the parallel timer container, the list filter, Start-mode popover, presence dialog and settings, hours basis, rounding and timer-rule cards, charts): gray instead of slate, `rounded-md` controls and `rounded-lg` cards and popovers instead of `rounded-xl/2xl/3xl`, the Time Tracking accent (`bg-entity-solid`, `text-entity-text`, `bg-entity-subtle`) instead of the old primary/teal/indigo, and a lighter popover shadow. The presence dialog, the Start-mode popover and the phone timer sheet render outside the page, so they now carry the Time Tracking accent themselves. Class changes only; behaviour, test ids and texts are unchanged.

### v1.14.2-Orange (2026-11-23)
- **Everyone who tracks time can pick any project and create one** (`public/api/read_scope.php`, `public/sync.php`, new `public/api/time_projects.php`, `src/utils/workableProjects.ts`, `src/utils/readScope.ts`, `ProjectPicker.tsx`, `createPickerProject.ts`): before, a person without the Projects module only saw projects they manage, already logged time on or have a task on. A new colleague saw none and could not create one. Now the server sends them a slim list (ids and names only) of every active project, client and project type in `readScope.timePicker`. The time API accepts any existing project from anyone with Time tracking. "Create project" in the picker works for anyone with Time tracking = edit, through `api/time_projects.php` (name, client, type, default status; audit-logged as `project.create.time_tracking`). Opening or editing a project still needs the Projects module.
  - The `forbidden_project` message no longer says "start from a task"; new codes `name_required`, `type_not_found`, `client_not_found`.
- **Tests**: `workableProjects.test.ts` (slim list with client and status, fallback to names from an older server, session-created projects kept until synced, picker clients and project types).

### v1.14.3-Orange (2026-11-23)
- **MCP: an Employee's agent can fill in their own time entries, and a refusal names the missing permission** (`public/api/mcp.php`, `mcp_ext_modules.php`): a refused tool call now says why, e.g. `Forbidden: this key may not call update_time_entry (the role "Employee" needs edit access to time_tracking).`, or that the tool does not exist, so whoever owns the key knows what to ask an administrator for in Settings → Roles. The `list_time_entries`, `update_time_entry` and `log_time_entry` descriptions now say that an entry's name is `description` and its work description is `note`, and that an entry linked to a task or ticket takes its name from that task or ticket. When `update_time_entry` gets a `description` for a linked entry, its reply carries a `notice` saying the name was not stored, so the agent doesn't take it as saved. Listing another user's entries without `time_tracking_team` now tells the caller their own user id.
- **Tests**: MCP probe `employee role: own time entries`. A key with the native Employee role lists only its own entries, sets the name and note of its own entry, gets the notice on a task-linked entry, and is refused another user's entry. A role with view-only time tracking is told which permission it lacks.
- **The Performance Dashboard is now the Dashboard** (new `src/utils/dashboardSection.ts`, `App.tsx`, `Sidebar.tsx`, `StartMenu.tsx`, `moduleCatalog.ts`, `permissions.ts`, `Dashboard.tsx`): the section at `#dashboard` shows the Performance Dashboard (until now "Analytics" at `#overview`), titled "Dashboard", in the Dashboard's place in the sidebar, the start menu, Visible modules, default pages and the landing route. Its tabs are unchanged. The Analytics entry is hidden and `#overview` links open `#dashboard`. Access follows the Analytics (`overview`) permission, so roles that could not see these company metrics still cannot. The widget board stays in the code behind `LEGACY_WIDGET_DASHBOARD` and each company's saved board (the `__home__` custom dashboard) is left untouched in the database; setting the flag to `true` brings both back as they were.
- **Tests**: `permissions.test.ts` (the Dashboard route is guarded by the permission of the screen it shows).
- **Roles: the Dashboard permission is the one that opens the Dashboard** (`permissions.ts` `ROLE_MATRIX_SECTIONS` / `roleMatrixTextKey`, `SettingsView.tsx`, `translations.ts`): with the Performance Dashboard in the Dashboard section, the old `dashboard` key guarded only the hidden widget board, yet the matrix still offered it as "Home dashboard". The matrix now leaves that row out and shows the `overview` toggle (which guards the Dashboard) inside the Dashboard section as "Dashboard", next to Custom dashboards; the separate Analytics section is gone. Stored role values are unchanged, so restoring `LEGACY_WIDGET_DASHBOARD` brings back the old rows with the values each role had.
- **Tests**: `permissions.test.ts` (the matrix hides `dashboard`, moves `overview` into the Dashboard section and still offers every other key once).
- **New role permission "Create projects from time tracking"** (`time_tracking_create_projects`; `src/utils/permissions.ts`, `public/api/permissions.php`, `public/api/read_scope.php`, `public/api/time_projects.php`, `App.tsx`, `createPickerProject.ts`): Settings → Users & roles → Time tracking now has a toggle that decides whether a role may create a project from the time-tracking project picker without the Projects module. It needs Time tracking = edit and is on by default, for existing roles too, so nothing changes until an admin turns it off. Picking any active project is not affected. The server refuses `api/time_projects.php` without it (403 `forbidden`). Roles with Projects = edit keep creating projects as before. Settings → Time tracking → "Who sees what" shows which roles have it.
- **Tests**: `permissions.test.ts` (section keys, legacy default on); RBAC probe TP1–TP3 (slim picker list carries ids/names/client/status only; create allowed by default; refused and nothing written with the toggle off).
