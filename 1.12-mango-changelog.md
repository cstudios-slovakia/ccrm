# Update 1.12 (Codename: Mango) — New Features

This document tracks all new features, architectural changes, schema migrations, and improvements introduced in the 1.12 Mango update cycle.

### v1.12.33-Mango (2026-10-15)
- **Sidebar: the footer stays visible and the nav scrolls above it (`src/components/Sidebar.tsx`)**: the bottom actions (expand / edit layout / settings / logout) were inside the scrolling `<nav>` and could be pushed out of view on a short window. They are now a sibling of the nav, pinned under it (`shrink-0`, `relative z-10`), so only the module list scrolls. In dock mode the nav now scrolls too, widened past the sidebar edge (`-mr-16`, click-through strip) so magnified icons are not clipped.

### v1.12.34-Mango (2026-10-15)
- **Visible Modules: the switch knob no longer shrinks (`src/components/VisibleModulesSettings.tsx`)**: the knob combined `inline-block` with `flex`, so the browser had to pick one, and a narrow flex item could squash it into an oval. It is now `inline-flex shrink-0`, a fixed 20 px circle with its check / cross centred.

### v1.12.35-Mango (2026-10-15)
- **Module setup wizard (`src/components/ModuleSetupWizard.tsx`, `src/utils/moduleWizard.ts`, `src/utils/moduleCatalog.ts`, `src/App.tsx`, `src/components/VisibleModulesSettings.tsx`, `src/components/SettingsView.tsx`)**:
  - **A large popup for choosing the workspace's modules**: a 2-column grid (1 column on phones) of cards, each with a real screenshot, the module's icon, title and category, a 2–3 sentence description in English, Slovak and Hungarian, and a visible switch (the whole card toggles). Changes are a draft until **Confirm**; **Decide later**, the close button and Escape leave the modules alone. A sticky header carries the "N of M active" counter (animated) and *Show All Modules*; a sticky footer carries Confirm. Confirm is refused, with an inline message, when every module would be hidden (the sidebar and Start menu would be empty). `role="dialog"`, `aria-modal`, focus trapped while open and returned on close, every card is one tab stop operated with Space / Enter.
  - **Opens by itself once for a brand-new admin, never for an existing one**: the first-login preferences migration (the only moment a never-seen account is observable, because it writes the `preferences` blob a moment after sign-in) records `moduleWizardPending` for an admin with no blob and no pre-migration traces in the browser. Confirm and Decide later stamp `moduleWizardCompletedAt`, so it does not return. Both flags live in `users.metadata_json.preferences`; no backend change (`ccrm_merge_user_metadata()` passes unknown keys through).
  - **Manual launch**: Settings → Visible Modules gets a *Run module setup wizard* button (admins only). It opens the wizard pre-filled with the current `integrationsConfig.disabledModules`.
  - **One shared module list**: `useModuleCatalog()` replaces the inline list in `VisibleModulesSettings.tsx`, so Settings and the wizard list the same modules with the same ids (built-ins, custom dashboards `dash_<id>`, registries `ue_<id>`, social media). Settings looks and behaves as before.
  - **Writes the same field the same way as Settings**: `updateIntegrationsConfig(prev => ({ ...prev, disabledModules }))`; disabled ids the catalog no longer lists (an archived dashboard) are kept.
- **Module screenshots (`scripts/capture-module-screenshots.mjs`, `public/module-screenshots/*.webp`)**: `npm run shots:modules` photographs every module's landing view against the invented demo dataset (no real data) in a fixed frame and writes WebP files of at most 150 KB (about 0.9 MB in total). The images are one Slovak-language set for now; per-language sets are planned. They ship because Vite copies `public/` into `dist/` and `php ccrm update` publishes `public/*`.
- **Tests**: `src/utils/moduleWizard.test.ts` (14), `tests/e2e/moduleSetupWizard.spec.ts` (new admin / existing admin / non-admin, Confirm → sidebar + Start menu + reload, Decide later, Settings launch, keyboard, empty-app guard, layout at 390 and 1440), a dark-mode overlay test, and scoping in `scripts/qa/run-qa.mjs`. The QA fixture's seeded admin now carries a preferences blob (an existing user) and the mock remembers a pushed `integrationsConfig`; `installBackendMocks` takes `{ user, themeMode }`.

### v1.12.36-Mango (2026-10-16)
- **Module setup wizard is now a first-installation step, not a per-admin one (`src/utils/moduleWizard.ts`, `src/App.tsx`)**: it used to open for every brand-new admin account, and each one's Confirm overwrote `disabledModules`, i.e. the modules every user of the workspace sees. It now opens by itself only for the first admin of a workspace where no other account has been through its first login, and never again after anyone has confirmed or skipped it.
  - **Workspace stamp**: Confirm and Decide later write `integrationsConfig.moduleSetupCompletedAt` (alongside the per-user `moduleWizardCompletedAt`). `shouldMarkModuleWizardPending` refuses to mark a new admin when that stamp is set or when any other account already has a preferences blob, and `shouldShowModuleWizard` re-checks the stamp, so an admin marked earlier is not shown it after someone else finished.
  - After the first run, modules are changed by hand in Settings → Visible Modules; *Run module setup wizard* there still works for admins. Existing installs are unaffected (their accounts already carry preferences).
  - **Tests**: three new unit tests in `moduleWizard.test.ts`; a new e2e case (new admin on an in-use workspace gets no wizard); the QA fixture's `installBackendMocks` takes `extraUsers`.

### v1.12.37-Mango (2026-10-16)
- **Projects list: new "Still to be paid" column (`src/utils/projectColumns.ts`, `src/utils/projectSort.ts`, `src/components/ProjectsView.tsx`)**: shows the same figure as "Still to be paid to us" on a project's Finances tab (invoiced but unpaid plus not invoiced yet, i.e. value minus what has been received). It is a built-in column placed after *Invoicable*, hidden by default like *Value* and *Invoicable*; turn it on in the project type's column editor. ### v1.12.38-Mango (2026-10-16)
- **Invoicable is now worked out one way everywhere (`src/components/ProjectsView.tsx`, `src/components/Dashboard.tsx`, `src/components/DynamicDashboardView.tsx`)**: the projects list and the two dashboard status-equation loops each carried their own copy of `value − Σ(amountReal || amountPlanned)`, which disagreed with the project's Finances tab. All three now use `resolveProjectValue` + `projectBilling` (`src/utils/projectBilling.ts`), so *Invoicable* is exactly the Finances tab's "Not invoiced yet" and *Invoiced* is its received + invoiced-unpaid.
  - **What changes in the numbers**: a **cancelled** invoice no longer counts as invoiced (Invoicable goes up); a **partly paid** invoice counts in full, paid part plus the unpaid rest, instead of only the paid part (Invoicable goes down); on the dashboards a project with no value no longer falls back to `project.budget`, a cost ceiling, which was being added to revenue. Projects with only paid or open invoices are unchanged. The `invoicesOffers` fallback on the dashboards, used when there are no finance records at all, is kept as it was.
  - **Tests**: a regression case in `projectBilling.test.ts` for the 4 015 € project (1 338,33 received, 2 676,66 open → 0,01 not invoiced, 2 676,67 still to be paid). The QA audit was not run for this build.

### v1.12.32-Mango (2026-10-15)
- **Login background no longer lags on Windows (`public/shanshui.html`, `src/components/ShanShuiBackground.tsx`, `src/components/LoginView.tsx`)**: the Shan Shui landscape is ~43,000 SVG polylines (~850,000 points), and the page changed the SVG `viewBox` on every frame, so Chrome re-rasterised the whole scene on the CPU 60 times a second. Apple Silicon hides that; a typical Windows PC does not.
  - **Compositor-only scrolling**: the SVG is drawn once into its own layer (`will-change: transform`, sized in px) and slid sideways with `translate3d` in `applyScroll()`. `rebase()` re-anchors the SVG at the camera whenever the chunks are re-rendered, in the same task, so there is no visible jump. Framing on narrow windows is unchanged (height fits, sides are cropped evenly).
  - **No `mix-blend-mode: multiply`**: it was set on the SVG and on the vignette overlay, forcing a full-screen blend of the animated iframe every frame. Multiply is linear in the source colour, so `poly()` now multiplies each colour by the paper's mean colour (`PAPER`, 240,228,204) once at generation time and blends normally: same result, alpha included. The `white` occluding fills become the paper colour. Same seed and scroll position as the old version: mean difference 1.66 / 255 per pixel, 0.01 % of pixels differ by more than 12; the only visible change is that paper grain no longer shows through inside the mountain fills.
  - **No backdrop blur over the animation**: the login card loses `backdrop-blur-2xl` (`bg-white/85` → `bg-white/94` to keep the text legible), so the blur is no longer recomputed every frame.
  - **Measured** (headless Chromium, software rendering, same seed, 1920×1080): median frame 1000–1550 ms → 67–133 ms. Absolute numbers are inflated by CPU rendering; the ratio is the point.
  - **Known remaining cost**: every ~256 world units (~10 s) the chunks are re-rendered through `innerHTML`, re-parsing ~14 MB of SVG. Not changed here.

### v1.12.29-Mango (2026-10-15)
- **Server-side permission enforcement for orders and tickets (`sync.php`, `api/orders.php`, `api/tickets.php`, mirrored in `public/`)**:
  - **Read gates (`sync.php` GET)**: `orders` is sent only with `orders` view; `tickets` and `supportContracts` only with `tickets` view. Withheld collections arrive as `[]` and are listed in `readScope.restricted`, so the client never reads them as deleted. `settings.ticketStatuses` / `ticketSettings` travel as `null` without `tickets`.
  - **Write and delete guards (`sync.php` POST)**: `orders` had no guard at all (any role could create, change and delete orders); it now needs `orders` edit and `orders.delete`. `tickets` and `supportContracts` already needed edit but anyone with edit could delete; deletes now need `tickets.delete`. `view` is read-only everywhere.
  - **Ticket data on other modules**: a task's `relatedTicketId`, a project's widget / public-board setup (including `ticketPublicHash`, the key to the public board), a lead's ticket e-mail whitelist and the ticket settings are withheld without `tickets` and cannot be changed without `tickets` edit. Saving a task or project without `tickets` keeps the stored values (the `null` the client was sent no longer erases a link or resets the widget). Documented in `docs/db_integration_notes/RBAC_SYSTEM.md`.
  - **Standalone endpoints**: `orders.php` GET needs `orders`, POST / DELETE need edit (+ `orders.delete`), guest-to-client conversion also needs `clients` edit; `tickets.php` `test_imap` / `poll_imap` / `send_email_reply` need `tickets` edit. The public status board and widget are unchanged.
  - **Tests**: `npm run test:rbac` gains the `T-R` / `T-W` / `T-X` / `T-E` groups (four new roles, nothing / view / edit / edit + delete); the new checks fail against the previous code and pass now. R7 ignores `dataVersion`, which cannot match a baseline that predates the orders / ticket tables.
